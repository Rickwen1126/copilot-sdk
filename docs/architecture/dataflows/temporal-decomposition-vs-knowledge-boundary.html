Architecture Learning Diagram

Temporal Decomposition vs Knowledge Boundary

Temporal decomposition feels clean because it follows runtime order. The trap is that every step can end up understanding the same protocol. Knowledge-boundary decomposition asks a different question: which design decision should be hidden here, and who is allowed to know it?

Bad: split by time

Each box is small, but the Codex wire shape leaks through all of them. A protocol change becomes shotgun surgery.

receive

Knows raw Codex event envelope.

parse

Knows event names and payload variants.

map

Knows Codex fields and Copilot output shape.

emit

Still checks protocol-specific tool state.
→→→✕
Repeated knowledge event.type, payload.toolCall, approval assumptions, and session lifecycle rules show up in many places.
Failure smell A Codex protocol tweak forces edits in receive, parse, map, emit, and tests.

Sample: thin temporal layers

function receiveCodexEvent(raw: unknown) {
  if (!isCodexEvent(raw)) throw new Error("bad codex event");
  return parseCodexEvent(raw);
}

function parseCodexEvent(event: CodexWireEvent) {
  if (event.type === "tool_call") {
    return mapToolCall(event.payload.toolCall);
  }
  return mapMessage(event.payload);
}

function mapToolCall(toolCall: CodexWireToolCall) {
  // Still knows Codex wire fields.
  return {
    kind: "copilot_tool_call",
    name: toolCall.function.name,
    arguments: toolCall.function.arguments,
  };
}

Good: split by hidden knowledge

Each boundary owns one kind of knowledge. Raw Codex protocol is normalized once; Copilot SDK presentation happens at the edge.

Codex reader

Only place that knows wire protocol.

Runtime event

Internal stable language.

Copilot presenter

Only place that knows SDK output contract.

Harness

Checks behavior, not private protocol details.
→→→✓
Contained knowledge Codex fields live in the reader. Copilot response shape lives in the presenter. Tests assert the normalized behavior.
Change behavior If Codex protocol changes, only reader + reader tests should move.

Sample: knowledge-boundary layers

type RuntimeEvent =
  | { kind: "assistant_text"; text: string }
  | { kind: "tool_call"; name: string; inputJson: string };

function readCodexEvent(event: CodexWireEvent): RuntimeEvent {
  switch (event.type) {
    case "assistant_message":
      return { kind: "assistant_text", text: event.payload.text };
    case "tool_call":
      return {
        kind: "tool_call",
        name: event.payload.toolCall.function.name,
        inputJson: event.payload.toolCall.function.arguments,
      };
  }
}

function presentToCopilot(event: RuntimeEvent): CopilotSdkEvent {
  switch (event.kind) {
    case "assistant_text":
      return { type: "message", content: event.text };
    case "tool_call":
      return {
        type: "tool_call",
        name: event.name,
        arguments: event.inputJson,
      };
  }
}
Reflex question: when you split a module, do not ask “what happens first?” Ask “which piece of knowledge is allowed to exist here?” If two modules must both understand the same protocol detail, the split is probably temporal, not architectural.
